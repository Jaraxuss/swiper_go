# 一、痛点回顾：批量生成为什么这么难？

上一篇只解决了"如何生成一页/几页高质量 HTML"的问题。

但现实的需求是：一份完整的产品介绍材料，往往有 10～20 个页面，涵盖章节页、痛点分析、功能详解、结果展示等多种类型。**如何批量且稳定地生成这些页面，让它们风格统一、质量如一，才是真正的挑战。**

我们先回顾一下前文末尾提到的两个方案：**基于 Gem（Gemini 的自定义助手）** 和 **基于 Antigravity（本地 AI 开发平台）**。我们逐一拆解它们的局限性。

---

## 方案 A：基于 Gemini Gem

Gem 本质上是一个有"系统提示词"的 Gemini 会话，方便快速上手，但在批量生成场景下很快会撞上天花板：

1. **局限于浏览器沙盒环境**
  
    Gem 无法操作本地文件系统。对于需要嵌入**图片、视频、音频**的复杂页面，Gem 只能生成一个"留白"的占位结构，后续所有的媒体素材都要靠手工补填。批量生成时，这个工作量是线性增长的——页面越多，手工填补的坑越多。
    
2. **动画效果无法真实验证**
  
    Gem 生成的 HTML 代码，在浏览器（CANVAS）中是"活的"（有动画），但如果是截图放到 PPTX 演示，就是静态图了；
    
    如果要完整动画，就得把完整的 HTML 代码复制到本地运行，但一次演示往往有很多页面，页面之间需要有切换（类似 PPT 的按下键播放下一页），而这个逻辑，是很难通过 Gem 生成的（因为这是个外部脚本，所以才有了 SwiperGo 这个项目）。
    
3. **上下文过长，整合时效果极差**
  
    也许你会想到："那就让 Gem 直接一次生成整份文稿，把所有页面打包在一个 HTML 文件里，用 JavaScript 进行页面切换，不就行了？"
    
    这个思路在技术上可行，但在实践中几乎不可用。一份 15 页的完整文稿，包含大量布局细节和样式代码，会让 Gem 的上下文迅速饱和。**越到后面，生成的页面质量越不稳定**——色系会偏移，组件会丢失，布局会简化退行。
    
    而一旦某个页面、某个布局出了问题，不得不重新生成**整个项目**，代价极高。
    

## 方案 B：基于 Antigravity（本地 AI 开发平台）

Antigravity 相比 Gem 有本质的优势：它可以直接读写本地文件，执行脚本，对项目有完整的"感知"。在生成新的页面时，能够基本仿照现有文件的代码逻辑，比如，在之前的文件中，为了使得离线也能运行，一些样式和图标资源文件都下载到了本地。在生成新的页面时，这些逻辑能够基本一致（这在 Gem 中就不可行了，因为 Gem 运行在浏览器，无法访问本地的文件）：

但是，如果只是在 Antigravity 中和 AI Agent 对话，你很快会发现瓶颈：

### 纯会话形式

这是最直觉的做法。每次打开一个新对话，告诉 AI 这次要生成什么内容，然后把它写入文件。

**局限性一：效率低**

每次对话生成一个页面，生成后发现哪里不对的（比如布局不合理、内容溢出），再要求 AI 去改。等他改好，检查没问题后再生成下一个。这样质量有保证，但是效率很低。

你也许会想到，一个会话跑的时候，我再开几个新会话同时生成不就行了？

**局限性二：重开会话，每次都要"重新教"AI**

不行。页面的风格要求 —— 用什么色系、什么布局、什么动画节奏 —— 全都藏在某次历史对话的多轮问答里。**会话窗口关了，这些要求也跟着消失了。** 下次打开新对话，你需要重新描述一遍规范，而 AI 对之前的上下文毫无记忆。

你可能会问：那我让 AI 批量生成不行吗（比如把资料都放在某个目录里）？

**局限性三：多轮对话导致约束力衰退**

如果在同一个会话中不断给 AI 喂资料生成新页面，哪怕你每次都提醒它"请参考第一页的风格"，质量依然会肉眼可见地下降。
这是因为随着对话历史的堆叠，那些在最初制定的**"核心规范"**（颜色取值、边距大小）逐渐被淹没在了海量的上下文之中。AI 其实在努力"理解"，但历史负担太重了。

可能没有试过 Antigravity、Cursor 这类工具的同学对这个质量下降不是很有概念，那我们用 Antigravity 的 WorkFlow 来尝试一下这个过程，直观看到结果。

对于 WorkFlow，先简单地介绍一下（后面我们还会用到他）：

### WorkFlow

简单来说，**WorkFlow 是将多次手工对话步骤编排起来的"自动化流水线"**。
比如：第一步读取文档，第二步分析内容，第三步生成代码。它极大地解放了人类守在屏幕前不断敲回车的双手。

总体来说，WorkFlow 是一种更进阶的方案：把多次对话的步骤编排成一个自动化流程，从而实现"一键批量生成"的效果。

    而过多留白的问题，在这个会话的前部分，是提过要求的：
    
    ![image.png](%E4%BB%8E%20%E8%83%BD%E7%94%A8%20%E5%88%B0%20%E5%A5%BD%E7%94%A8%20%EF%BC%9AAgent%20Skill%20%E5%A6%82%E4%BD%95%E8%A7%A3%E5%86%B3%E6%89%B9%E9%87%8F%20HTML%20%E7%94%9F%E6%88%90%E7%9A%84%E8%B4%A8%E9%87%8F%E7%93%B6%E9%A2%88/image%205.png)
    
    生成质量不高的原因，我认为有两个：
    
    **原因一：注意力稀疏（Attention Dilution）**
    
    模型的注意力机制是有限的。在一个超长的会话里，它不得不在"理解你的当前需求"和"记住你三十轮前设定的色系规范"这两件事之间不断权衡分配。随着上下文增长，早期的约束不断被稀释，失重，直到彻底被忽略。
    
    这不是某个具体 AI 的缺陷，**这是当前所有大语言模型架构的固有局限**（超长上下文带来的"大海捞针"效应始终存在，模型更容易关注最新输入的信息，而遗忘早期的条件指令）。
    
    所以我们需要一个办法，能尽量**让每一次生成任务，都处于一个全新、干净的上下文环境里，不受历史长对话的干扰。**
    
    **原因二：自然语言的主观性与折损（需求模糊）**
    
    这在使用大模型的时候很常见。由于我们是用自然语言发出指令，这就带来了巨大的解释空间：
    
    - 当生成页面时，要求 AI 「留白不要多」 —— 什么叫不多？是 16px 还是 24px？
    - 当做图生图时，要求 AI 保持产品和背景「严丝合缝」 —— 边缘阈值是多少？光影羽化需要多少像素？
    - 当想要一个科技感页面时，要求 AI 「看上去更有科技感」 —— 是加霓虹边框、用冷蓝配色、还是增加毛玻璃效果？
    - 当想要一个柔和的动效时，要求 AI 「动画别太生硬」 —— ease-in-out 的参数该怎么写？0.3s 还是 0.5s？
    
    这些要求如果不转化为具体的代码标准、色值 Token 和固定参数，AI 每次的"理解"都会产生波动。我们必须通过制定绝对客观的规范，来消除这种语言的模糊性。
    

---

因此，核心问题不在于哪款工具更好，而在于**「在批量任务中，如何克服模型注意力稀疏，同时将主观意图转化为客观绝对的约束力」**。有没有一种方式，能让每次生成都像"第一次生成"一样专注、高质量，并且 100% 遵守开发规范？

在目前的 Agent 工程实践中，提供了一个极具操作性和性价比的解决方案：**Agent Skill**。

# 二、什么是 Agent Skill？

## 一句话定义

**Agent Skill 就是写给 AI 看的标准作业程序（SOP）**，以文件的形式固化在项目的文件系统中，让 AI 在任意时刻、任意对话窗口都能调用它，并得到一致的输出结果。

如果说传统的"系统提示词"是写在 AI 记忆里的、会随着会话消失的便签，那么 Agent Skill 就是印在档案库里的、永久存档的操作手册。

## 它长什么样？

一个 Skill 本质上是一个 Markdown 文件（通常命名为 `SKILL.md`），存放在项目的 `.agent/skills/{skill-name}/` 目录下。比如：

```
.agent/
└── skills/
    ├── html_style_summary/        # Skill 1：HTML 风格总结
    │   └── SKILL.md               # 这个 Skill 的 SOP
    └── generate_html_from_material/   # Skill 2：根据资料生成 HTML
        └── SKILL.md
```

`SKILL.md` 里的内容很详细，大致包含：

- **名称与描述**（让 AI 能自动识别）
- **输入参数说明**（告诉用户调用时需要提供什么）
- **分步操作流程**（Step 1 → Step 2 → Step 3…，类似 SOP）
- **输出规范**（结果保存到哪、格式是什么）

一个 AI IDE（如 Antigravity、CodeX、Claude Code 等）读取到项目中存在的 Skill 后，会将其注册为可调用的能力模块。用户只需在对话中用自然语言触发它”使用 HTML 风格总结 Skill，分析以下页面……“，AI 便会按照 `SKILL.md` 中定义的步骤，有条不紊地执行：

## 它解决了什么问题？

回到前文提到的"注意力稀疏"问题，Agent Skill 从根本上改变了信息传递的方式：

| 对比维度 | 传统长会话 | Agent Skill 架构 |
| --- | --- | --- |
| **1. 规则存储位置** | 会话上下文（随关闭消失） | 文件系统中的 `SKILL.md`（永久保存） |
| **2. 上下文记忆质量** | 随轮次增加而逐渐稀释遗忘 | 每次都是全新、纯粹的计算环境 |
| **3. 约束力与模糊性** | 主观词汇易被误解（"留白少点"） | 绝对代码标准（"padding: 16px"） |
| **4. 跨会话一致性** | ❌ 几乎没有，取决于运气 | ✅ 完全一致，代码级复刻 |
| **5. 跨模型可移植性** | ❌ 强依赖某一次的会话历史 | ✅ 任何接入工作流的 AI 都可读取 |
| **6. 团队协作共享** | ❌ 只存在于个人的聊天记录中 | ✅ 可随项目提交代码仓库，团队共用 |

> 其中第三点非常实用：
> 
> 
> 如今各家的 AI IDE 都是有配额的，大量使用时，可能会触发5小时限额甚至周限额，导致降智。有了 Agent Skill，可以上午用 Antigravity 生成，下午用 Claude 生成，明天再用 CodeX 生成，结果一样稳定（后续我们看看更换模型的效果）。
> 

## Agent Skill 的概念从哪里来？

很多经常看 AI 圈新闻的朋友可能会问，这不就是 Anthropic (Claude) 提出的 "Computer Use" 吗？或者是 OpenAI 的 "Tool Use"？

确实，大模型调用外部工具（Tool API）的能力是由这些基础大模型厂商原生提供的。
但用一份**包含 YAML 头信息和 Markdown 语法描述的 `SKILL.md` 文件**来固化业务级流程的“Agent Skill”，其实是随着 Cursor、Windsurf、Antigravity（Cline 架构分支）等一众原生 AI IDE 普及后，在近半年由**开发者社区和 Agent 工程工具链探索总结出的一种最佳实践**。

Anthropic 提供了"手"，但 Agent Skill 是教会这只手如何干活的"作业指导书"。

其核心思想来自软件工程的一个老概念：**"分离关注点"**。

- **关注点一：规则与规范** → 固化进 Skill 文件，永久存档，AI 读取
- **关注点二：当前任务的具体输入** → 由用户在每次对话中实时提供

这种分离让 AI 每次执行任务时，都只需要关注两件事：一份清晰的 SOP + 一份具体的当前输入。**没有冗余历史，没有稀释的注意力，只有高度聚焦的执行。**

---

## 它还能用来做什么？

HTML 页面批量生成只是一个具体应用。从方法论来看，任何满足以下条件的工作，都适合用 Agent Skill 来固化：

1. **有可复用的规范或模板**（设计规范、代码风格、文档格式）
2. **需要重复执行多次**（批量生成、定期自动化任务）
3. **输入内容每次不同，但处理逻辑相同**（每次的素材不一样，但生成流程是固定的）

一些可以延伸的方向：

- 📄 **代码规范固化**：把团队的 API 接口规范、错误处理规范写进 Skill，让 AI 自动按规范生成代码。
- 📊 **数据报告生成**：把报告的格式要求、品牌色系、固定章节结构写进 Skill，每次只喂原始数据即可。
- 🖼️ **图片处理流水线**：把图片尺寸规范、命名规则、输出路径写进 Skill，AI 自动处理一批素材。
- 📝 **文档翻译与本地化**：把术语对照表、口吻风格写进 Skill，AI 翻译时自动遵守团队约定。

# 三、实战：用两个 Skill 完成稳定批量生成演示文稿

说完概念，回到项目。为了解决批量 HTML 生成的质量问题，我最终拆分出了两个相互配合的 Skill，分别负责"沉淀规范"和"按规范生成"两个阶段。

---

## 第一步：沉淀规范 → HTML 风格总结 Skill

**核心思路**：与其每次在对话里告诉 AI "要用红色竖条作为装饰"，不如让 AI 去读几个"已经做得很好"的示范页面，自己总结出一套设计规范，并把它永久写入文件。

**调用方式**（对话触发，一次性执行）：

![image.png](%E4%BB%8E%20%E8%83%BD%E7%94%A8%20%E5%88%B0%20%E5%A5%BD%E7%94%A8%20%EF%BC%9AAgent%20Skill%20%E5%A6%82%E4%BD%95%E8%A7%A3%E5%86%B3%E6%89%B9%E9%87%8F%20HTML%20%E7%94%9F%E6%88%90%E7%9A%84%E8%B4%A8%E9%87%8F%E7%93%B6%E9%A2%88/image%206.png)

**AI 的执行流程**：

1. 启动本地 HTTP 服务
2. 逐个用浏览器打开并截图分析这些页面
3. 提取背景色、组件结构、动画规律、Tailwind 类名约定等设计细节
4. 将总结结果以标准格式写入 `.agent/skills/html_style_summary/` 目录

**输出成果**：一份包含**设计规范、HTML 结构模板、CSS 类名约定、动画规则**的完整 Markdown 文档。这份文档从此永久存储在项目中：

最关键的是：**这份总结，凝聚的是"最佳样本页面"中所有细节的精华，而不是某次对话的记忆**。它不会稀释，不会消失，不会随着会话关闭而丢失。

```
├── 02_标准含视频详情页.md
├── 03_一般详情页.md
├── 04_详情页_背景_痛点_方案_价值_细节.md
└── 05_启动会首页风格.md
```

## 第二步：按规范生成 → 根据资料生成 HTML 页面 Skill

有了风格总结文件作为"地基"，批量生成就变得极其简单。**每次生成一个新页面，我都会新开一个对话窗口**，然后调用这个 Skill：

![image.png](%E4%BB%8E%20%E8%83%BD%E7%94%A8%20%E5%88%B0%20%E5%A5%BD%E7%94%A8%20%EF%BC%9AAgent%20Skill%20%E5%A6%82%E4%BD%95%E8%A7%A3%E5%86%B3%E6%89%B9%E9%87%8F%20HTML%20%E7%94%9F%E6%88%90%E7%9A%84%E8%B4%A8%E9%87%8F%E7%93%B6%E9%A2%88/image%2010.png)

**AI 的执行流程**：

收到指令后，AI 的思考与执行完全遵照 Skill 的"冷酷"指挥：

1. **查阅规则**：读取指定的风格总结文件（`02_标准含视频详情页风格.md`）
2. **分析素材**：解析我在此次对话中提供的原始资料（如视频演示的业务点、新加入的一张架构图）。
3. **对照与组装**：将解析出的素材内容，按风格规范里的「标准尺寸」、「预设动画参数」、「品牌红色值」进行 1:1 的组装。
4. **验证保存**：保存到本地对应目录，通过本地服务预览效果。

**为什么这个方式质量极高且稳定？**

因为在这个对话窗口里，AI 面对的**上下文极其结构化且非常短小**，我们可以来算一笔"Token 账"（Token 是大模型处理文本和图片的计费单元，也是衡量上下文压力的指标）：

- **风格总结文件（绝对规范）**：约 500-1000 Tokens
- **本次素材（如输入了一张 1080P 产品图 + 几句旁白描述）**：约 1000-1500 Tokens
- **对话提示指令**：小于 100 Tokens

**总上下文不超过 3000 Tokens**，这远远低于任何现代大模型的"注意力疲劳"阈值。AI 完全不需要在"记忆几万字的历史包袱"和"理解当前需求"之间做任何权衡 —— 面对这样干净、高信息密度的环境，它两件事都能做到接近 100% 的完美。

这就解释了标题里的观点：**Agent Skill 把 AI 从"状态机"变成了"无状态函数"**。

- **状态机（传统会话）**：AI 像一个带病工作的人，需要拼命回忆上一轮、上十轮、上百轮的历史对话状态才能决定当下怎么做。
- **无状态函数（Skill 架构）**：AI 像一个精准的函数公式 `y = f(x)`，每次调用它，它只认入参（当前素材 x）和规则本身（Skill 规律 f），绝不受历史杂念干扰，输出结果高度可重现。

# 六、使用 Agent Skill 进一步完善

细心的你会发现：

类似下方示例（1和2）这类演示文稿，其中有些专业架构图或数据产品截图我们是不希望 AI 去"脑补"画出来的，而是希望把原始素材（可能包含在客户发来的 PPTX 或 PDF 里）抠出来直接贴在上半部分，这样交给客户看起来更有说服力。而且不用大模型去生成这种图，翻车概率也极低。下面我们就动手用 Skill 来实现：

**调用方式**（对话触发）：
- **输入**：`pdf_path`（源文件绝对路径）和 `target_page`（提取页码）。

**AI 的执行流程**：

收到指令后，AI 将严格按照《从 PDF 提取高质量图片资源 Skill》的操作手册有条不紊地执行：

1. **提取全景底图**：调用底层工具将指定页面渲染为 300dpi 高清大图，并利用大模型的视觉能力（Vision）读取左上角文字，以此自动命名工作目录。
2. **无损素材剥离**：使用 `pdfimages` 瞬间从 PDF 底层剥离所有内嵌的“原生底片”（无任何 AI 缩放或篡改），导出为散装图片库。
3. **AI 智能分拣与清洗（核心所在）**：AI Agent 开始发挥大脑的作用，对散图进行地毯式审查。自动过滤无意义的线段、小黑点等噪点，精准分拣出系统截图、软件 Logo；针对原属 PDF 的灰阶蒙版层，还会自动调用工具完成透明度（Alpha）图像的合并修复。
4. **生成数据归档**：将筛选完成的核心素材移动并重命名，自动生成标准的 `assets_manifest.json` 资产清单文件，以供下游组装。

# 八、总结与展望：售后/CS服务的"轻量化 RPA"跃迁

回顾这次从"长对话失败"到"引入 Agent Skill 成功批量产出"的整个探索过程，虽然载体是 HTML 页面，但它背后揭示的方法论，与我们每天在做的**"客户成功（CS）与项目实施"**有着极强的共鸣。

> **不要试图让 AI（或新员工）在一个超长的上下文里"记住所有口口相传的细节"。**
> **而是要把团队中优秀的"隐性经验"，封装成可执行的 Skill（显性知识块），让机器去完成稳定、聚焦的复制执行。**

过去，我们要么靠"口头传授"让实施同学记住做工单的标准；要么耗费巨大的开发资源，去把一条不常变化的售后流程写成系统代码。

而现在，**Agent Skill 本质上提供了一种"极低门槛的轻量化业务流封装"能力**：

1. **经验显性化**：每个高质量的演示方案、每种刁钻的报错处理方式，被提炼成 `SKILL.md`，这就是我们在售后服务中无形的**公司资产**。
2. **能力即插即用**：团队新同学不用再从头摸索交付规范，只要在对话框里调用前辈沉淀好的 Skill，就能用最强的大模型跑出老员工级别的高标准产出。
3. **机器知识协同**：Skill 文件可以随着业务变化不断打磨升级，成为整个售后实施团队共同拥有的"业务操作系统"。我们在让大模型打工的同时，也在沉淀一套属于团队专属的"超级外脑"。

接下来，我计划继续在这套体系上做针对售后实施的深度探索，包括：

- 引入 `extract_pdf_assets` Skill，直接从客户提供的业务说明 PDF 和 Excel 里提取痛点与数据，再流转到演示页生成 Skill。
- 探索多 Skill 之间的链式调用（Skill Chain），让工单排查、回复生成、Wiki 录入一口气自动流转完成。

如果你和你的团队也在被 AI 生成质量的"波峰波谷"反复折磨，或者对如何用 Agent Skill 赋能交付与实施有更好的实践思路，欢迎在评论区随时交流。
