# 一、痛点回顾：批量生成为什么这么难？

上一篇只解决了"如何生成一页/几页高质量 HTML"的问题。

但现实的需求是：一份完整的产品介绍材料，往往有 10～20 个页面，涵盖章节页、痛点分析、功能详解、结果展示等多种类型。**如何批量且稳定地生成这些页面，让它们风格统一、质量如一，才是真正的挑战。**

我们先回顾一下前文末尾提到的两个方案：**基于 Gem（Gemini 的自定义助手）** 和 **基于 Antigravity（本地 AI 开发平台）**。我们逐一拆解它们的局限性。

---

## 方案 A：基于 Gemini Gem

Gem 本质上是一个有"系统提示词"的 Gemini 会话，方便快速上手，但在批量生成场景下很快会撞上天花板：

1. **局限于浏览器沙盒环境**
    
    Gem 无法操作本地文件系统。对于需要嵌入**图片、视频、音频**的复杂页面，Gem 只能生成一个"留白"的占位结构，后续所有的媒体素材都要靠手工补填。批量生成时，这个工作量是线性增长的——页面越多，手工填补的坑越多。
    
2. **动画效果无法真实验证**
    
    Gem 生成的 HTML 代码，在浏览器（CANVAS）中是"活的"（有动画），但如果是截图放到 PPTX 演示，就是静态图了；
    
    如果要完整动画，就得把完整的 HTML 代码复制到本地运行，但一次演示往往有很多页面，页面之间需要有切换（类似 PPT 的按下键播放下一页），而这个逻辑，是很难通过 Gem 生成的（因为这是个外部脚本，所以才有了 SwiperGo 这个项目）。
    
3. **上下文过长，整合时效果极差**
    
    也许你会想到："那就让 Gem 直接一次生成整份文稿，把所有页面打包在一个 HTML 文件里，用 JavaScript 进行页面切换，不就行了？"
    
    这个思路在技术上可行，但在实践中几乎不可用。一份 15 页的完整文稿，包含大量布局细节和样式代码，会让 Gem 的上下文迅速饱和。**越到后面，生成的页面质量越不稳定**——色系会偏移，组件会丢失，布局会简化退行。
    
    而一旦某个页面、某个布局出了问题，不得不重新生成**整个项目**，代价极高。
    

## 方案 B：基于 Antigravity（本地 AI 开发平台）

Antigravity 相比 Gem 有本质的优势：它可以直接读写本地文件，执行脚本，对项目有完整的"感知"。在生成新的页面时，能够基本仿照现有文件的代码逻辑，比如，在之前的文件中，为了使得离线也能运行，一些样式和图标资源文件都下载到了本地。在生成新的页面时，这些逻辑能够基本一致（这在 Gem 中就不可行了，因为 Gem 运行在浏览器，无法访问本地的文件）：

但是，如果只是在 Antigravity 中和 AI Agent 对话，你很快会发现瓶颈：

### 纯会话形式

这是最直觉的做法。每次打开一个新对话，告诉 AI 这次要生成什么内容，然后把它写入文件。

**局限性一：效率低**

每次对话生成一个页面，生成后发现哪里不对的（比如布局不合理、内容溢出），再要求 AI 去改。等他改好，检查没问题后再生成下一个。这样质量有保证，但是效率很低。

你也许会想到，一个会话跑的时候，我再开几个新会话同时生成不就行了？

**局限性二：重开会话，每次都要"重新教"AI**

不行。页面的风格要求 —— 用什么色系、什么布局、什么动画节奏 —— 全都藏在某次历史对话的多轮问答里。**会话窗口关了，这些要求也跟着消失了。** 下次打开新对话，你需要重新描述一遍规范，而 AI 对之前的上下文毫无记忆。

你可能会问：那我让 AI 批量生成不行吗（比如把资料都放在某个目录里）？

**局限性三：多轮对话导致质量下降**

# 二、什么是 Agent Skill？

## 一句话定义

**Agent Skill 就是写给 AI 看的标准作业程序（SOP）**，以文件的形式固化在项目的文件系统中，让 AI 在任意时刻、任意对话窗口都能调用它，并得到一致的输出结果。

如果说传统的"系统提示词"是写在 AI 记忆里的、会随着会话消失的便签，那么 Agent Skill 就是印在档案库里的、永久存档的操作手册。

## 它长什么样？

一个 Skill 本质上是一个 Markdown 文件（通常命名为 `SKILL.md`），存放在项目的 `.agent/skills/{skill-name}/` 目录下。比如：

```
.agent/
└── skills/
    ├── html_style_summary/        # Skill 1：HTML 风格总结
    │   └── SKILL.md               # 这个 Skill 的 SOP
    └── generate_html_from_material/   # Skill 2：根据资料生成 HTML
        └── SKILL.md
```

`SKILL.md` 里的内容很详细，大致包含：

- **名称与描述**（让 AI 能自动识别）
- **输入参数说明**（告诉用户调用时需要提供什么）
- **分步操作流程**（Step 1 → Step 2 → Step 3…，类似 SOP）
- **输出规范**（结果保存到哪、格式是什么）

一个 AI IDE（如 Antigravity、CodeX、Claude Code 等）读取到项目中存在的 Skill 后，会将其注册为可调用的能力模块。用户只需在对话中用自然语言触发它”使用 HTML 风格总结 Skill，分析以下页面……“，AI 便会按照 `SKILL.md` 中定义的步骤，有条不紊地执行：

## 它解决了什么问题？

回到前文提到的"注意力稀疏"问题，Agent Skill 从根本上改变了信息传递的方式：—— 前面我加上了关于需求的明确性，所以我希望这里相关的描述能提到

| 对比维度 | 传统对话 | Agent Skill |
| --- | --- | --- |
| **1. 规则存储位置** | 会话上下文（随关闭消失） | 文件系统（永久保存） |
| **2. 每次任务的上下文质量** | 随轮次增加而稀释 | 每次都是全新、干净的上下文 |
| **3. 跨会话一致性** | ❌ 几乎没有 | ✅ 完全一致 |
| **4. 跨模型可移植性** | ❌ 依赖特定会话历史 | ✅ 任何支持 Skill 的 AI 都可读取 |
| **5. 协作共享** | ❌ 只存在于个人会话中 | ✅ 可存在于代码仓库，团队可共用 |

> 其中第三点非常实用：
> 
> 
> 如今各家的 AI IDE 都是有配额的，大量使用时，可能会触发5小时限额甚至周限额，导致降智。有了 Agent Skill，可以上午用 Antigravity 生成，下午用 Claude 生成，明天再用 CodeX 生成，结果一样稳定（后续我们看看更换模型的效果）。
> 

## AI Skill 的概念从哪里来？

Agent Skill 并非某家公司的私有概念，它是近两年 **"AI Agent 工程化"**浪潮中涌现出来的一种实践范式。—— 这个应该是错误的？我记得 Agent Skill 是 Anthropic 发明的，帮我核实，如果我是正确的，帮我修正表述

其核心思想来自软件工程的一个老概念：**"分离关注点"**。

- **关注点一：规则与规范** → 固化进 Skill 文件，永久存档，AI 读取
- **关注点二：当前任务的具体输入** → 由用户在每次对话中实时提供

这种分离让 AI 每次执行任务时，都只需要关注两件事：一份清晰的 SOP + 一份具体的当前输入。**没有冗余历史，没有稀释的注意力，只有高度聚焦的执行。**

---

## 它还能用来做什么？

HTML 页面批量生成只是一个具体应用。从方法论来看，任何满足以下条件的工作，都适合用 Agent Skill 来固化：

1. **有可复用的规范或模板**（设计规范、代码风格、文档格式）
2. **需要重复执行多次**（批量生成、定期自动化任务）
3. **输入内容每次不同，但处理逻辑相同**（每次的素材不一样，但生成流程是固定的）

一些可以延伸的方向：

- 📄 **代码规范固化**：把团队的 API 接口规范、错误处理规范写进 Skill，让 AI 自动按规范生成代码。
- 📊 **数据报告生成**：把报告的格式要求、品牌色系、固定章节结构写进 Skill，每次只喂原始数据即可。
- 🖼️ **图片处理流水线**：把图片尺寸规范、命名规则、输出路径写进 Skill，AI 自动处理一批素材。
- 📝 **文档翻译与本地化**：把术语对照表、口吻风格写进 Skill，AI 翻译时自动遵守团队约定。

# 三、实战：用三个 Skill 完成稳定批量生成演示文稿

说完概念，回到项目。为了解决批量 HTML 生成的质量问题，我最终拆分出了两个相互配合的 Skill，分别负责"沉淀规范"和"按规范生成"两个阶段。

---

## 第一步：沉淀规范 → HTML 风格总结 Skill

**核心思路**：与其每次在对话里告诉 AI "要用红色竖条作为装饰"，不如让 AI 去读几个"已经做得很好"的示范页面，自己总结出一套设计规范，并把它永久写入文件。

**调用方式**（对话触发，一次性执行）：

![image.png](%E4%BB%8E%20%E8%83%BD%E7%94%A8%20%E5%88%B0%20%E5%A5%BD%E7%94%A8%20%EF%BC%9AAgent%20Skill%20%E5%A6%82%E4%BD%95%E8%A7%A3%E5%86%B3%E6%89%B9%E9%87%8F%20HTML%20%E7%94%9F%E6%88%90%E7%9A%84%E8%B4%A8%E9%87%8F%E7%93%B6%E9%A2%88/image%206.png)

**AI 的执行流程**：

1. 启动本地 HTTP 服务
2. 逐个用浏览器打开并截图分析这些页面
3. 提取背景色、组件结构、动画规律、Tailwind 类名约定等设计细节
4. 将总结结果以标准格式写入 `.agent/skills/html_style_summary/` 目录

**输出成果**：一份包含**设计规范、HTML 结构模板、CSS 类名约定、动画规则**的完整 Markdown 文档。这份文档从此永久存储在项目中：

最关键的是：**这份总结，凝聚的是"最佳样本页面"中所有细节的精华，而不是某次对话的记忆**。它不会稀释，不会消失，不会随着会话关闭而丢失。

```
html_style_summary/
├── 01_章节页.md
├── 02_标准含视频详情页.md
├── 03_一般详情页.md
├── 04_详情页_背景_痛点_方案_价值_细节.md
└── 05_启动会首页风格.md
```

## 第二步：按规范生成 → 根据资料生成 HTML 页面 Skill

有了风格总结文件作为"地基"，批量生成就变得极其简单。**每次生成一个新页面，我都会新开一个对话窗口**，然后调用这个 Skill：

![image.png](%E4%BB%8E%20%E8%83%BD%E7%94%A8%20%E5%88%B0%20%E5%A5%BD%E7%94%A8%20%EF%BC%9AAgent%20Skill%20%E5%A6%82%E4%BD%95%E8%A7%A3%E5%86%B3%E6%89%B9%E9%87%8F%20HTML%20%E7%94%9F%E6%88%90%E7%9A%84%E8%B4%A8%E9%87%8F%E7%93%B6%E9%A2%88/image%2010.png)

### **AI 的执行流程**：（底下流程是不太正确的，根据图片重写，比如应该是先分析Skill.md）

1. 读取对应的风格总结文件（`02_标准含视频详情页风格.md`）
2. 解析用户提供的资料（标题、要点、视频路径等）
3. 严格按照风格文件中的规范生成 HTML
4. 保存到指定路径，并在本地预览验证

### **为什么这个方式质量稳定？**

这个对话窗口里，AI 的上下文极其干净：—— 以下换算为 token，并且我提供的素材包含图片，帮我分析一个常见的1080p图片消耗多少token，然后修改表达（并且不仅要有注意力相关表述，还要有需求明确的表达）

- 风格总结文件（设计规范）：约 500-1000 字
- 用户当前提供的素材：约 200-500 字

**总上下文不超过 1500 字**，远低于任何模型的有效注意力范围。AI 不需要在"记忆历史约束"和"理解当前需求"之间做任何权衡 —— 两件事它都能做到几乎 100%。

Agent Skill 把 AI 从"**状态机**"变成了"**无状态函数**"：

- **状态机**：需要依赖之前的历史上下文（状态）才能正确工作
- **无状态函数**：每次调用只依赖当前的输入（Skill 文件 + 当前素材），输出结果高度可预期

# 七、总结与展望

—— 底下这个描述有点偏开发了，虽然我之前是开发，但现在是影刀售后的客户成功，请帮我转换表达

回顾这整个探索过程，我想提炼出一个核心方法论供团队参考：

> **不要试图让 AI 在一个超长的会话里"记住所有细节"。而是要把"有价值的规则和规范"固化进文件系统，让 AI 每次都在一个干净、聚焦的环境中执行任务。**
> 

这不是某种特别神秘的技术，本质上就是软件工程中"配置与代码分离"思想在 AI 工作场景下的投影。

**目前这套流程已经相当成熟，主流 AI IDE 基本都支持 Agent Skill（Antigravity、Cursor、Windsurf 等）**，这意味着：

1. 你可以根据不同任务的特点，选择最合适的模型来执行 Skill（比如图片分析用多模态强的模型，代码生成用代码能力强的模型）
2. 团队成员可以共享 Skill 文件，不需要每个人都从头摸索规范
3. Skill 文件可以随着项目演进不断迭代优化，形成团队的"AI 工作记忆"

接下来，我计划继续在这套体系上做探索，包括：

- 引入 `extract_pdf_assets` Skill，直接从 PDF 素材中提取文字和图片，再流转到生成 Skill
- 探索 Skill 之间的链式调用（Skill Chain）
