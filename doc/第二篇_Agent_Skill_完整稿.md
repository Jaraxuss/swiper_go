# 从"能用"到"好用"：Agent Skill 如何解决批量 HTML 生成的质量瓶颈

---

## 一、痛点回顾：批量生成为什么这么难？

上一篇只解决了"如何生成**一页**高质量 HTML"的问题。

但现实的需求是：一份完整的产品介绍材料，往往有 10～20 个页面，涵盖章节页、痛点分析、功能详解、结果展示等多种类型。**如何批量且稳定地生成这些页面，让它们风格统一、质量如一，才是真正的挑战。**

当时能想到的方案，大致分为两条路：**基于 Gem（Gemini 的自定义助手）** 和 **基于 Antigravity（本地 AI 开发平台）**。我们逐一拆解它们的局限性。

---

### 方案 A：基于 Gemini Gem

Gem 本质上是一个有"系统提示词"的 Gemini 会话，方便快速上手，但在批量生成场景下很快会撞上天花板：

**① 局限于浏览器沙盒环境**

Gem 无法操作本地文件系统。对于需要嵌入**图片、视频、音频**的复杂页面，Gem 只能生成一个"留白"的占位结构，后续所有的媒体素材都要靠手工补填。批量生成时，这个工作量是线性增长的——页面越多，手工填补的坑越多。

**② 动画效果无法真实验证**

Gem 生成的 HTML 代码，在浏览器中是"活的"（有动画），但很多团队成员仍然习惯把演示内容导成 PPTX 或截图分享。一旦截图，动画效果荡然无存，回到了出发点。

**③ 上下文过长，整合时效果极差**

你也许会想："那就让 Gem 直接一次生成整份文稿，把所有页面打包在一个 HTML 文件里，用 JavaScript 切换不就行了？"

这个思路在技术上可行，但在实践中几乎不可用。一份 15 页的完整文稿，包含大量布局细节和样式代码，会让 Gem 的上下文迅速饱和。**越到后面，生成的页面质量越不稳定**——色系会偏移，组件会丢失，布局会简化退行。而一旦某个页面出了问题，你不得不重新生成**整个项目**，代价极高。

---

### 方案 B：基于 Antigravity（本地 AI 开发平台）

Antigravity 相比 Gem 有本质的优势：它可以直接读写本地文件，执行脚本，对项目有完整的"感知"。但在批量生成场景下，同样暴露出了核心矛盾。

#### B-1：纯会话形式（一次对话生成一个页面）

这是最直觉的做法。每次打开一个新对话，告诉 AI 这次要生成什么内容，然后把它写入文件。

**局限性一：每次都要"重新教"AI**

页面的风格要求——用什么颜色、哪种组件、什么动画节奏——全都藏在某次历史对话的多轮问答里。**会话窗口关了，这些要求也跟着消失了。** 下次打开新对话，你需要重新描述一遍规范，而 AI 对之前的上下文毫无记忆。

**局限性二：效率随页面数量线性下降**

每次对话只能处理少量素材（附件上传有数量限制），生成一个页面后，还要手工检查、调整、保存。生成 15 个页面，就得重复 15 次这套流程。

#### B-2：使用 WorkFlow（自动化编排多轮对话）

WorkFlow 是一种更进阶的方案：把多次对话的步骤编排成一个自动化流程，从而实现"一键批量生成"的效果。从理论上，这似乎解决了效率问题。

但我实际测试后，发现它只是把"人工重复"换成了"机器重复"，根本矛盾没有被解决。

---

## 二、真正的敌人：注意力稀疏（Attention Dilution）

无论是手工多轮对话，还是 WorkFlow 自动化批量，**它们都在同一个上下文空间内运转**。随着对话轮次增加、上下文越来越长，大语言模型会开始"遗忘"那些早期设定的细节约束。

这个现象，我把它叫做**注意力稀疏（Attention Dilution）**。

模型的注意力机制是有限的。在一个超长的会话里，它不得不在"理解你的当前需求"和"记住你三十轮前设定的色系规范"这两件事之间不断权衡分配。随着上下文增长，早期的约束不断被稀释，失重，直到彻底被忽略。

这不是某个具体 AI 的缺陷，**这是当前所有大语言模型架构的固有局限**。

---

## 三、用数据说话：WorkFlow vs Skill 的生成质量差异

为了让这个问题更加直观，我准备了 10 组对比案例，每组都是"相同内容素材，分别用 WorkFlow 和 Skill 生成"的 HTML 页面对比。

（*此处放置 10 组对比截图*）

AI 对这 10 组对比图的整理总结如下：

---

### 1. 关键业务板块丢失（Section Omission）

这是最显著的问题。WorkFlow 往往只能抓住核心的"需求背景"和"主流程"，而忽略了支撑页面"专业感"的辅助板块：

- **丢失详情图表**：在"文件内容对比"中，AI Power 工作流架构图和对比结果预览表格被整体省略。
- **丢失业务规模展示**：在"物料到货计划拆分"和"每日发货流程自动化"中，精美的业务规模数字卡片被简化或删除。
- **丢失文件/邮件预览**：在"图片批量归档"和"发货流程"中，模拟真实业务场景的图纸文件类型和邮件驱动预览板块消失。

---

### 2. 结构与布局退化（Layout Degradation）

WorkFlow 的布局趋向"简单化"和"扁平化"：

- **多列转单列**：Skill 能维持复杂的右侧边栏或双栏布局，WorkFlow 往往退化为简单的上下堆叠，视觉重心失衡。
- **空间利用率低**：生成的页面常出现大面积无意义的空白，或者内容挤成一团，缺乏层级感。
- **内容溢出或错位**：缺乏样式约束时，图标和文字出现排列不齐或超出容器的情况。

---

### 3. 视觉与品牌一致性丧失（Visual Inconsistency）

由于注意力分散，WorkFlow 无法持续维持初始设定的设计规范：

- **图标库混杂**：在同一个流程图中使用的图标风格不统一（大小不一、线条粗细不同）。
- **头部/底部样式偏移**：在较后的案例（Case 05、Case 10）中，页面头部突然变成黑底，失去了品牌统一的渐变白风格；页码、面包屑等细节元素时有时无。
- **配色与装饰丢失**：侧边装饰条、渐变背景阴影、微交互视觉提示（勾选框、进度点）等细节被逐一抛弃。

---

### 4. 信息颗粒度粗化（Information Thinning）

WorkFlow 对原始资料的还原度较低：

- **数据模糊化**：将"94家供应商、1090颗物料"简化为"海量数据处理"，丢失了业务的说服力。
- **步骤合并**：Skill 能清晰展示 5-6 步的详细操作流程；WorkFlow 常常将其合并为 3 步，导致业务逻辑展示不完整。

---

### 5. 交互与细节功能缺失（Functional Loss）

- **丢失辅助链接**：在复杂表单页面，Skill 会生成"点我查看更多"等交互引导，WorkFlow 则只剩下一张死板的示意图。
- **标签与角标丢失**：WorkFlow 容易忽略卡片上的小标签（"自动识别触发"、"MES导出"等身份标识）。

---

### 小结

> **WorkFlow 的生成更像是一个"概括版"**——核心逻辑在，但失去了表现力、专业度和细节严谨性。
>
> 它的本质问题不是工具本身，而是它没能解决"上下文中的规则如何被稳定传递"这个问题。每一次生成，规则的传递都是不完整的、会衰减的。

这就引出了一个关键问题：**有没有一种方式，能让每次生成都像"第一次生成"一样专注、高质量？**

答案就是：**Agent Skill**。

---

## 四、破局之道：什么是 Agent Skill？

### 一句话定义

**Agent Skill 就是写给 AI 看的标准作业程序（SOP）**，以文件的形式固化在项目的文件系统中，让 AI 在任意时刻、任意对话窗口都能调用它，并得到一致的输出结果。

如果说传统的"系统提示词"是写在 AI 记忆里的、会随着会话消失的便签，那么 Agent Skill 就是印在档案库里的、永久存档的操作手册。

---

### 它长什么样？

一个 Skill 本质上是一个 Markdown 文件（通常命名为 `SKILL.md`），存放在项目的 `.agent/skills/{skill-name}/` 目录下。它包含：

```
.agent/
└── skills/
    ├── html_style_summary/        # Skill 1：HTML 风格总结
    │   └── SKILL.md               # 这个 Skill 的 SOP
    └── generate_html_from_material/   # Skill 2：根据资料生成 HTML
        └── SKILL.md
```

`SKILL.md` 里的内容很朴实：

- **名称与描述**（YAML frontmatter，让 AI IDE 能自动识别）
- **输入参数说明**（告诉用户调用时需要提供什么）
- **分步操作流程**（Step 1 → Step 2 → Step 3…，类似 SOP）
- **输出规范**（结果保存到哪、格式是什么）

一个 AI IDE（如 Antigravity、Cursor、Windsurf 等）读取到项目中存在的 Skill 后，会将其注册为可调用的能力模块。用户只需在对话中用自然语言触发它："请使用 HTML 风格总结 Skill，分析以下页面……"，AI 便会按照 `SKILL.md` 中定义的步骤，有条不紊地执行。

---

### 它解决了什么问题？

回到前文提到的"注意力稀疏"问题，Agent Skill 从根本上改变了信息传递的方式：

| 对比维度 | 传统对话 / WorkFlow | Agent Skill |
|----------|---------------------|-------------|
| **规则存储位置** | 会话上下文（随关闭消失） | 文件系统（永久保存） |
| **每次任务的上下文质量** | 随轮次增加而稀释 | 每次都是全新、干净的上下文 |
| **跨会话一致性** | ❌ 几乎没有 | ✅ 完全一致 |
| **跨模型可移植性** | ❌ 依赖特定会话历史 | ✅ 任何支持 Skill 的 AI 都可读取 |
| **协作共享** | ❌ 只存在于个人会话中 | ✅ 存在于代码仓库，团队可共用 |

其中最关键的一点是最后一行：**Skill 文件存在于项目仓库中，不属于任何一个会话或任何一个人**。团队成员 A 总结的风格规范，团队成员 B 可以直接调用；今天用 Gemini 生成，明天用 Claude 生成，结果一样稳定。

---

### AI Skill 的概念从哪里来？

Agent Skill 并非某家公司的私有概念，它是近两年 **"AI Agent 工程化"**浪潮中涌现出来的一种实践范式。

其核心思想来自软件工程的一个老概念：**"分离关注点（Separation of Concerns）"**。

- **关注点一：规则与规范** → 固化进 Skill 文件，永久存档，AI 读取
- **关注点二：当前任务的具体输入** → 由用户在每次对话中实时提供

这种分离让 AI 每次执行任务时，都只需要关注两件事：一份清晰的 SOP + 一份具体的当前输入。**没有冗余历史，没有稀释的注意力，只有高度聚焦的执行。**

---

### 它还能用来做什么？（发散思考）

HTML 页面批量生成只是一个具体应用。从方法论来看，任何满足以下条件的工作，都适合用 Agent Skill 来固化：

1. **有可复用的规范或模板**（设计规范、代码风格、文档格式）
2. **需要重复执行多次**（批量生成、定期自动化任务）
3. **输入内容每次不同，但处理逻辑相同**（每次的素材不一样，但生成流程是固定的）

一些可以延伸的方向：

- 📄 **代码规范固化**：把团队的 API 接口规范、错误处理规范写进 Skill，让 AI 自动按规范生成代码。
- 📊 **数据报告生成**：把报告的格式要求、品牌色系、固定章节结构写进 Skill，每次只喂原始数据即可。
- 🖼️ **图片处理流水线**：把图片尺寸规范、命名规则、输出路径写进 Skill，AI 自动处理一批素材。
- 📝 **文档翻译与本地化**：把术语对照表、口吻风格写进 Skill，AI 翻译时自动遵守团队约定。

## 五、实战拆解：我是如何用两个 Skill 完成稳定批量生成的

说完概念，回到我自己的项目。为了解决批量 HTML 生成的质量问题，我最终拆分出了两个相互配合的 Skill，分别负责"沉淀规范"和"按规范生成"两个阶段。

---

### 第一步：沉淀规范 → `HTML 风格总结` Skill

**核心思路**：与其每次在对话里告诉 AI "要用红色竖条作为装饰"，不如让 AI 去读几个"已经做得很好"的示范页面，自己总结出一套设计规范，并把它永久写入文件。

**调用方式**（对话触发，一次性执行）：

```
请使用 HTML 风格总结 Skill，分析以下页面：
- 页面类型：标准含视频详情页
- 页面列表：
  - ./pages/custom/直播自动化.html
  - ./pages/custom/图纸识别.html
- 输出文件名：02_标准含视频详情页风格.md
```

**AI 的执行流程**：

1. 启动本地 HTTP 服务
2. 逐个用浏览器打开并截图分析这些页面
3. 提取背景色、组件结构、动画规律、Tailwind 类名约定等设计细节
4. 将总结结果以标准格式写入 `.agent/skills/html_style_summary/` 目录

**输出成果**：一份包含**设计 Token、HTML 结构模板、CSS 类名约定、动画规则**的完整 Markdown 文档。这份文档从此永久存储在项目中。

```
html_style_summary/
├── 01_章节页风格.md
├── 02_标准含视频详情页风格.md
└── 03_一般详情页风格.md
```

最关键的是：**这份总结，凝聚的是"最佳样本页面"中所有细节的精华，而不是某次对话的记忆**。它不会稀释，不会消失，不会随着会话关闭而丢失。

---

### 第二步：按规范生成 → `根据资料生成 HTML 页面` Skill

有了风格总结文件作为"地基"，批量生成就变得极其简单。**每次生成一个新页面，我都会新开一个对话窗口**，然后调用这个 Skill：

```
请使用「根据资料生成 HTML 页面」Skill：
- 页面风格：标准含视频详情页
- 页面标题：超复杂表单识别并填写
- 视频路径：./assets/超复杂表单识别.mp4
- 功能要点：
  1. 自动识别表单字段类型
  2. 智能填写关联数据
  3. 异常字段自动标注
```

**AI 的执行流程**：

1. 读取对应的风格总结文件（`02_标准含视频详情页风格.md`）
2. 解析用户提供的资料（标题、要点、视频路径等）
3. 严格按照风格文件中的规范生成 HTML
4. 保存到指定路径，并在本地预览验证

**为什么这个方式质量稳定？**

这个对话窗口里，AI 的上下文极其干净：

- 风格总结文件（设计规范）：约 500-1000 字
- 用户当前提供的素材：约 200-500 字

**总上下文不超过 1500 字**，远低于任何模型的有效注意力范围。AI 不需要在"记忆历史约束"和"理解当前需求"之间做任何权衡——两件事它都能做到 100%。

这就是为什么我说，**Agent Skill 把 AI 从"状态机"变成了"无状态函数"**：

- **状态机**：需要依赖之前的历史上下文（状态）才能正确工作
- **无状态函数**：每次调用只依赖当前的输入（Skill 文件 + 当前素材），输出结果高度可预期

## 七、总结与展望

回顾这整个探索过程，我想提炼出一个核心方法论供团队参考：

> **不要试图让 AI 在一个超长的会话里"记住所有细节"。**
> **而是要把"有价值的规则和规范"固化进文件系统，让 AI 每次都在一个干净、聚焦的环境中执行任务。**

这不是某种特别神秘的技术，本质上就是软件工程中"配置与代码分离"思想在 AI 工作场景下的投影。

**目前这套流程已经相当成熟，主流 AI IDE 基本都支持 Agent Skill（Antigravity、Cursor、Windsurf 等）**，这意味着：

1. 你可以根据不同任务的特点，选择最合适的模型来执行 Skill（比如图片分析用多模态强的模型，代码生成用代码能力强的模型）
2. 团队成员可以共享 Skill 文件，不需要每个人都从头摸索规范
3. Skill 文件可以随着项目演进不断迭代优化，形成团队的"AI 工作记忆"

接下来，我计划继续在这套体系上做探索，包括：

- 引入 `extract_pdf_assets` Skill，直接从 PDF 素材中提取文字和图片，再流转到生成 Skill
- 探索 Skill 之间的链式调用（Skill Chain）
